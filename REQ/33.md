# R-#33: Reorganize the source code in one repository with one private submodule

**Status:** `open`  
**Priority:** `high`  
**Repository:** `stable-sl` (branch `v3`)  
**Date:** 2026-09-08

---

## 📋 Description

Reorganize the source code structure of **stable-sl** into a single repository, integrating `coordinator-stable-sl` as a private submodule at `apps/stable-sl/app/api/`. This reorganization follows the `learn.tg` pattern and facilitates maintenance, deployment, and coordinated development of all components.

---

## 🎯 Objectives

1. **Unify** all code into a single repository (`stable-sl`).
2. **Preserve** the history of `coordinator-stable-sl` as a submodule.
3. **Adopt** the `learn.tg` structure (without Rails) for internal consistency.
4. **Use** `pnpm@10.6.2` with workspaces and catalogs for shared dependencies.
5. **Centralize** environment variables in `apps/.env.example` and `apps/.env`.
6. **Ensure** all components continue to work (frontend, API, contracts).
7. **Migrate** the API data layer from Drizzle to Kysely (dropping the Drizzle
   schema/migrations and starting from the current DB structure).
8. **Expose** the `m` CLI at `apps/stable-sl/bin/m` so `m` (including
   `ai:framework`, `ai:principles`, `ai:skill`, `db:*`, etc.) runs from the
   frontend app.

## 🖥️ `m` CLI from the frontend

`m` must be runnable from `apps/stable-sl/bin/m`. The `bin/m` script imports
`@pasosdejesus/mpdj` (for the `ai:framework`, `ai:principles`, `ai:skill`,
`ai:verify`, `ai:adJ` commands) and `@pasosdejesus/m/m` (core CLI), following
the `learn.tg` pattern:

```js
#!/usr/bin/env node
(async () => {
  try { await import('@pasosdejesus/mpdj') } catch {}
  await import('@pasosdejesus/m/m')
})()
```

`@pasosdejesus/m` and `@pasosdejesus/mpdj` must resolve to the **same** copy of
`@pasosdejesus/m` (single version, deduped peer) so the plugin command registry
is shared and `ai:framework`/`ai:principles`/`ai:skill` register correctly.

## 🗄️ Data layer: Drizzle → Kysely

- Replace `drizzle-orm` / `drizzle-kit` with `kysely` + `kysely-ctl`
  (config at `.config/kysely.config.ts`, `newKyselyPostgresql()` factory),
  following the `m` project convention.
- **Migrations:** the Drizzle migrations/schema are not migrated. They are
  deleted and the schema starts from the current DB structure (confirmed
  against the production dump `dump-stablesl.sql` restored into `stablesldev`).
- **Types:** use `numeric` instead of `real` for monetary/price/balance
  columns (`amountSle`, `amountCrypto`, `cryptoPriceInSle`, `cryptoBalance`,
  `newBalance`, `maximum`, `minimum`). Production uses `real` (float4), which
  is lossy for money.
- **Foreign keys + indexes:** added via Kysely migrations (they do not exist
  in production — only `PRIMARY KEY (id)`):
  - FK `purchaseorder.quoteId → purchasequote.id`
  - FK `salesorder.quoteId → salesquote.id`
  - FK `movementsmobile.salesOrderId → salesorder.id`
  - FK `movementsmobile.purchaseOrderId → purchaseorder.id`
  - Indexes: `purchaseorder(quoteId)`, `purchaseorder(token)`,
    `purchaseorder(state)`, `purchasequote(token)`, `salesorder(quoteId)`,
    `salesorder(token)`, `salesquote(token)`, `smslog(phoneNumber)`,
    `movementsmobile(salesOrderId)`, `movementsmobile(purchaseOrderId)`.
- **`DB` type:** use the `db.d.ts` generated by `kysely-codegen` from the
  restored production dump (see `stablesldev-db.d.ts`).
- **Current DB structure** (in `coordinator-stable-sl/db/schema.ts`) is the
  source of truth — 6 tables:

| Table | Columns |
|---|---|
| `purchasequote` | senderPhone, senderName, senderWallet, crypto, cryptoPriceInSle, maximum, minimum, timestamp, token |
| `purchaseorder` | quoteId, token, state, seconds, amountSle, crypto, amountCrypto, receiverPhone, receiverName, transactionUrl, timestampTx, timestampExpired, timestampSms, messageSms |
| `salesquote` | receiverPhone, receiverName, receiverWallet, senderPhone, senderName, crypto, cryptoPriceInSle, cryptoBalance, maximum, minimum, timestamp, token |
| `salesorder` | quoteId, token, state, seconds, amountSle, crypto, amountCrypto, cryptoBalance, senderPhone, senderName, receiverPhone, receiverName, transactionUrl, timestampTx, timestampExpired, timestampUssd, numberUssd, messageUssd |
| `smslog` | timestamp, ip, phoneNumber, message |
| `movementsmobile` | timestamp, amount, newBalance, salesOrderId, purchaseOrderId, other |

## 🧪 Testing

Unit tests are an acceptance criterion. Approach (mirrors `learn.tg`):

- **Runner:** Vitest (`vitest run`) with `jsdom` environment,
  `@testing-library/react` and `@testing-library/jest-dom`.
- **DB mocks:** `@pasosdejesus/m/test-utils/kysely-mocks` (`apiDbMocks`:
  `mockExecuteTakeFirst`, `mockExecute`, `mockSqlExecute`, `mockSql`,
  `mockPgPool`, `MockKysely`, `createMockKysely`).
- **Blockchain/auth/UI mocks:** `@pasosdejesus/m/test-utils/viem-mocks`,
  `@pasosdejesus/m/test-utils/rainbowkit-mocks` (`apiAuthMocks`), and
  `@pasosdejesus/m/test-utils/radix-mocks`.
- **`vitest.setup.ts`** registers `vi.mock('kysely', ...)` and
  `vi.mock('pg', ...)` at module scope (hoisted), plus the radix/rainbowkit/
  wagmi/siwe/axios mocks, exactly as `learn.tg/apps/nextjs/vitest.setup.ts`.
- **Scope:** unit tests for the DB layer (`db/database.test.ts`) and for the
  API route handlers (`app/api/*/route.ts`) using the Kysely mocks; component
  tests where valuable.
